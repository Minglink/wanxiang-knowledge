# CWE-805: 缓冲区访问长度值错误

## 缺陷定义

产品使用顺序操作来读取或写入缓冲区，但它使用了错误的长度值，导致其访问缓冲区边界之外的内存。

## 机制与扩展说明

当长度值超过目标缓冲区大小时，可能会发生缓冲区溢出。

## 可能后果及作用范围

此表指定了与该弱点相关的不同个体后果。“范围”识别被违规的应用安全领域，而“影响”描述如果攻击者成功利用该弱点所产生的负面技术影响。“可能性”提供有关相对于列表中其他后果，特定后果被预期的可能性信息。例如，某种弱点可能极有可能被利用以实现某种影响，但利用它来实现另一种影响的可能性则很低。
影响
详细信息
读取内存；修改内存；执行未经授权的代码或命令
范围：完整性、机密性、可用性
缓冲区溢出通常可用于执行任意代码，这通常超出了程序隐式安全策略的范围。这通常可用于破坏任何其他安全服务。
修改内存；DoS：崩溃、退出或重启；DoS：资源消耗 (CPU)
范围：可用性
缓冲区溢出通常会导致程序崩溃。其他导致可用性丧失的攻击也是可能的，包括使程序进入无限循环。

## 预防与缓解措施

阶段
缓解措施
需求
策略：
语言选择
使用一种不允许此弱点发生或提供使此弱点更容易避免的结构的语言。
例如，许多自行管理内存的语言，如 Java 和 Perl，不易受到缓冲区溢出的影响。其他语言，如 Ada 和 C#，通常提供溢出保护，但程序员可以禁用该保护。
请注意，即使语言本身在理论上是安全的，语言到原生代码的接口可能仍然容易受到溢出的影响。
架构与设计
策略：
库或框架
使用经过审查的库或框架，该库或框架不允许此弱点发生，或提供使此弱点更容易避免的结构。
示例包括 Messier 和 Viega 开发的安全 C 字符串库 (SafeStr) [
REF-57
]，以及微软的 Strsafe.h 库 [
REF-56
]。这些库提供了易于溢出的字符串处理函数的更安全版本。
注意：
这不是一个完整的解决方案，因为许多缓冲区溢出与字符串无关。
操作；构建与编译
策略：
环境强化
使用某些编译器或编译器扩展提供的自动缓冲区溢出检测机制。示例包括：Microsoft Visual Studio 的 /GS 标志、Fedora/Red Hat 的 FORTIFY_SOURCE GCC 标志、StackGuard 和 ProPolice，它们提供各种机制，包括基于金丝雀（canary）的检测和范围/索引检查。
来自 D3FEND 的 D3-SFCV (栈帧金丝雀验证) [
REF-1334
] 详细讨论了基于金丝雀的检测。
有效性：纵深防御
注意：
这不一定是一个完整的解决方案，因为这些机制只能检测某些类型的溢出。此外，结果仍然是拒绝服务，因为典型的响应是退出应用程序。
实施
在分配和管理应用程序内存时，请考虑遵循以下规则
仔细检查缓冲区是否确实如指定的那么大。
使用接受要复制的字节数的函数（如 strncpy()）时，请注意，如果目标缓冲区大小等于源缓冲区大小，它可能不会 NULL 终止字符串。
如果在循环中访问缓冲区，请检查缓冲区边界，并确保不会写入超出分配空间的内容。
必要时，在将所有输入字符串传递给复制和连接函数之前，将其截断为合理的长度。
架构与设计
对于在客户端执行的任何安全检查，请确保在服务器端重复这些检查，以避免
CWE-602
。攻击者可以通过在检查执行后修改值，或修改客户端以完全移除客户端检查来绕过这些检查。随后，这些被修改的值将被提交到服务器。
操作；构建与编译
策略：
环境强化
使用在内存中随机排列程序可执行文件和库位置的功能或扩展来运行或编译软件。由于这使得地址不可预测，它可以防止攻击者可靠地跳转到可利用的代码。
示例包括地址空间布局随机化 (ASLR) [
REF-58
] [
REF-60
] 和位置无关可执行文件 (PIE) [
REF-64
]。如果导入模块的默认内存地址与其他模块冲突，可以使用随机生成的地址对它们进行类似地重定向，这个过程称为“重定位”(Windows) 和“预链接”(Linux) [
REF-1332
]。库的 ASLR 不能与预链接结合使用，因为它需要运行时重定位库，这违背了预链接的目的。
有关这些技术的更多信息，请参阅 D3FEND 的 D3-SAOR (段地址偏移随机化) [
REF-1335
]。
有效性：纵深防御
注意：
这些技术并不能提供完整的解决方案。例如，漏洞利用程序经常利用公开内存地址的错误来最大化代码执行的可靠性 [
REF-1337
]。研究还表明，侧信道攻击可以绕过 ASLR [
REF-1333
]。
运营
策略：
环境强化
使用提供数据执行保护（使用硬件 NX 或 XD 位）的 CPU 和操作系统，或在软件中模拟此功能的等效技术，例如 PaX [
REF-60
] [
REF-61
]。这些技术确保执行的任何指令都仅位于属于代码段的内存地址处。
有关这些技术的更多信息，请参阅 D3FEND 的 D3-PSEP (进程段执行预防) [
REF-1336
]。
有效性：纵深防御
注：
这不是一个完整的解决方案，因为缓冲区溢出可能被用来覆盖附近的变量，以危险的方式修改软件状态。此外，它不能用于需要自修改代码的情况。最后，攻击仍然可能导致拒绝服务，因为典型的响应是退出应用程序。
架构与设计；运维
策略：
环境强化
以完成任务所需的最低权限运行代码 [
REF-76
]。如果可能，创建仅用于单个任务的、具有有限权限的隔离帐户。这样，成功的攻击不会立即让攻击者获得对产品其余部分或其环境的访问权限。例如，数据库应用程序在日常操作中通常不需要以数据库管理员身份运行。
架构与设计；运维
策略：
沙盒或囚笼
在“囚笼 (jail)”或类似的沙盒环境中运行代码，该环境在进程和操作系统之间强制执行严格的边界。这可以有效地限制在特定目录中可以访问哪些文件，或者软件可以执行哪些命令。
操作系统级别的示例包括 Unix chroot 囚笼、AppArmor 和 SELinux。通常，受管代码可能会提供一些保护。例如，Java SecurityManager 中的 java.io.FilePermission 允许软件对文件操作指定限制。
这可能不是一个可行的解决方案，并且它仅将影响限制在操作系统层面；应用程序的其余部分仍可能面临被妥协的风险。
小心避免
CWE-243
以及与囚笼相关的其他弱点。
有效性：有限
注：
此缓解措施的有效性取决于所使用的特定沙盒或囚笼的防护能力，可能仅有助于减小攻击范围，例如限制攻击者使用某些系统调用或限制可访问的文件系统部分。

## 检测与审计方法

方法
详细信息
自动化静态分析
该弱点通常可以使用自动化静态分析工具检测到。许多现代工具使用数据流分析或基于约束的技术来最大限度地减少误报。
自动静态分析在报告越界内存操作时通常不考虑环境因素。这可能使用户难以确定哪些警告应该优先调查。例如，分析工具可能会报告在非预期以 setuid 或其他特殊权限运行的程序中，源自命令行参数的缓冲区溢出。
有效性：高
注意：
缓冲区相关错误的检测技术比大多数其他弱点类型更成熟。
自动化动态分析
此弱点可以使用动态工具和技术进行检测，这些工具和技术通过使用具有许多多样化输入的大型测试套件与产品交互，例如模糊测试 (fuzzing)、健壮性测试和故障注入。产品的运行可能会变慢，但不应变得不稳定、崩溃或产生不正确的结果。
有效性：中等
注意：
在没有代码可见性的情况下，黑盒方法可能无法充分区分此弱点与其他弱点，需要人工方法来诊断根本问题。
人工分析
人工分析对于发现此弱点非常有用，但在有限的时间限制内可能无法达到理想的代码覆盖率。对于必须考虑所有输入的弱点，这变得很困难，因为攻击面可能太大。
自动化动态分析
使用在编译期间集成的工具，以插入与内存安全错误相关的运行时错误检查机制，例如用于 C/C++ 的 AddressSanitizer (ASan) [
REF-1518
]。
有效性：中等
注：
需要精心设计的输入才能到达包含错误的各种代码路径，例如由模糊测试工具生成的输入。此外，这些工具可能会降低性能，并且它们仅报告错误情况——而不是导致错误的原始失误。

## 官方英文定义（核对锚点）

Buffer Access with Incorrect Length Value

The product uses a sequential operation to read or write a buffer, but it uses an incorrect length value that causes it to access memory that is outside of the bounds of the buffer.
