# CWE-78：OS 命令中使用的特殊元素中和不当（“OS 命令注入”）

## 缺陷定义

产品使用来自上游组件的受外部影响的输入来构建全部或部分操作系统命令，但它没有中和或错误地中和了特殊元素，当这些元素被发送到下游组件时，可能会修改预期的操作系统命令。

## 机制与扩展说明

在攻击者无法直接访问操作系统（例如 Web 应用程序）的环境中，此弱点可能导致漏洞。或者，如果弱点发生在特权程序中，它可能允许攻击者指定通常无法访问的命令，或以攻击者本身不具备的权限调用替代命令。如果被破坏的进程不遵循最小权限原则，问题会变得更加严重，因为攻击者控制的命令可能会以特殊的系统权限运行，从而增加破坏程度。
OS 命令注入至少有两种子类型：
应用程序旨在执行其自身控制下的单个固定程序。它打算使用外部提供的输入作为该程序的参数。例如，程序可能会使用 system("nslookup [HOSTNAME]") 来运行 nslookup，并允许用户提供 HOSTNAME 作为参数。攻击者无法阻止 nslookup 执行。但是，如果程序没有从 HOSTNAME 参数中移除命令分隔符，攻击者可以将分隔符放入参数中，这允许他们在 nslookup 执行完成后执行他们自己的程序。
应用程序接受一个输入，并使用它完全选择要运行的程序以及要使用的命令。应用程序只是将整个命令重定向到操作系统。例如，程序可能会使用 "exec([COMMAND])" 来执行用户提供的 [COMMAND]。如果 COMMAND 处于攻击者控制之下，则攻击者可以执行任意命令或程序。如果使用 exec() 和 CreateProcess() 等函数执行命令，攻击者可能无法在同一行中组合多个命令。
从弱点角度来看，这些变体代表了不同的程序员错误。在第一个变体中，程序员明确打算将来自不可信方的输入作为要执行的命令中的参数的一部分。在第二个变体中，程序员并不打算让任何不可信方访问该命令，但程序员很可能没有考虑到恶意攻击者提供输入的其他方式。

## 可能后果及作用范围

此表指定了与该弱点相关的不同个体后果。“范围”识别被违规的应用安全领域，而“影响”描述如果攻击者成功利用该弱点所产生的负面技术影响。“可能性”提供有关相对于列表中其他后果，特定后果被预期的可能性信息。例如，某种弱点可能极有可能被利用以实现某种影响，但利用它来实现另一种影响的可能性则很低。
影响
详细信息
执行未经授权的代码或命令；DoS：崩溃、退出或重启；读取文件或目录；修改文件或目录；读取应用程序数据；修改应用程序数据；隐藏活动
范围：机密性、完整性、可用性、不可抵赖性
攻击者可能执行未经授权的操作系统命令，这些命令随后可用于禁用产品，或读取和修改攻击者无法直接访问的数据。由于目标应用程序正在直接执行命令而不是攻击者，因此任何恶意活动看起来都可能来自该应用程序或应用程序的所有者。

实施
策略：
输出编码
虽然使用动态生成的查询字符串、代码或将控制与数据混合的命令存在风险，但有时可能无法避免。请正确引用参数并转义这些参数中的任何特殊字符。最保守的方法是转义或过滤所有未通过极其严格的白名单检查的字符（例如，除字母数字或空格以外的所有字符）。如果仍需使用某些特殊字符（如空格），请在转义/过滤步骤后将每个参数用引号括起来。注意参数注入（
CWE-88
）。
实施
如果允许通过输入文件或标准输入指定要执行程序的参数，则考虑使用该模式来传递参数，而不是使用命令行。
架构与设计
策略：
参数化
如果可用，请使用自动强制执行数据和代码分离的结构化机制。这些机制可能能够自动提供相关的引用、编码和验证，而不是依赖开发人员在每次生成输出时提供此功能。
有些语言提供了多种可用于调用命令的功能。如果可能，识别任何使用单个字符串调用命令 shell 的功能，并将其替换为需要单独参数的功能。这些功能通常执行适当的参数引用和过滤。例如，在 C 语言中，system() 函数接受包含要执行的完整命令的字符串，而 execl()、execve() 等则需要字符串数组，每个参数一个。在 Windows 中，CreateProcess() 一次只接受一个命令。在 Perl 中，如果 system() 被提供了一个参数数组，那么它将引用每个参数。
实施
策略：
输入验证
假设所有输入都是恶意的。采用“接受已知良好”的输入验证策略，即使用严格符合规范的可接受输入列表。拒绝任何不严格符合规范的输入，或将其转换为符合规范的内容。
在执行输入验证时，考虑所有潜在相关的属性，包括长度、输入类型、可接受值的全部范围、缺失或额外的输入、语法、跨相关字段的一致性以及对业务规则的符合性。作为业务规则逻辑的一个例子，“boat”在语法上可能是有效的，因为它只包含字母数字字符，但如果输入只预期包含“red”或“blue”等颜色，则它无效。
不要仅仅依赖查找恶意或畸形输入。这很可能会遗漏至少一种不受欢迎的输入，尤其是当代码环境发生变化时。这可能给攻击者留出绕过预期验证的空间。不过，黑名单对于检测潜在攻击或确定哪些输入由于严重畸形而应被直接拒绝是有用的。
在构建 OS 命令字符串时，使用严格的允许列表，根据请求中参数的预期值限制字符集。这将间接限制攻击范围，但该技术不如正确的输出编码和转义重要。
请注意，适当的输出编码、转义和引用是防止 OS 命令注入的最有效解决方案，尽管输入验证可能提供一些纵深防御。这是因为它有效地限制了输出中会出现的内容。输入验证并不总是能防止 OS 命令注入，特别是如果您需要支持可能包含任意字符的自由格式文本字段。例如，在调用邮件程序时，您可能需要允许主题字段包含“;”和“>”等原本危险的输入，这些输入需要进行转义或以其他方式处理。在这种情况下，剥离字符可能会降低 OS 命令注入的风险，但它会导致不正确的行为，因为主题字段不会按用户预期的那样被记录。这看起来可能是一个小的不便，但在程序依赖结构良好的主题行以便将消息传递给其他组件时，它可能更重要。
即使您在验证中犯了错误（例如忘记了 100 个输入字段中的一个），适当的编码仍然很可能会保护您免受基于注入的攻击。只要不孤立地进行，输入验证仍然是一种有用的技术，因为它可以显著减少您的攻击面，让您能够检测到一些攻击，并提供适当编码无法解决的其他安全好处。

实施
确保错误消息仅包含对目标受众有用的最小细节，而不包含其他信息。消息需要在过于隐晦（可能使用户感到困惑）和过于详细（可能泄露不该泄露的信息）之间取得平衡。消息不应泄露用于确定错误的具体方法。攻击者可以利用详细信息来完善或优化其原始攻击，从而增加成功的可能性。
如果必须详细记录错误，请将其记录在日志消息中，但要考虑如果攻击者能够查看日志消息会发生什么。密码等高度敏感的信息绝不应保存到日志文件中。
避免使用不一致的消息，以免意外向攻击者透露内部状态，例如用户账户是否存在。
在 OS 命令注入的上下文中，传回给用户的错误信息可能会揭示是否正在执行 OS 命令，以及可能正在使用什么命令。
运营
策略：
沙盒或囚笼

运营
策略：
防火墙
使用可以检测针对此弱点的攻击的应用程序防火墙。在无法修复代码（因为由第三方控制）的情况下，或者作为应用更全面的软件保证措施时的应急预防措施，或者为了提供深度防御，这可能是有益的 [
REF-1481
]。
有效性：中等
注意：
应用程序防火墙可能无法覆盖所有可能的输入向量。此外，攻击者可能会使用绕过保护机制的攻击技术，例如使用仍可被接收输入的组件处理的畸形输入。根据功能的不同，应用程序防火墙可能会无意中拒绝或修改合法请求。最后，定制可能需要一些人工投入。
架构与设计；运维
策略：
环境强化

REF-76

CWE-95

该弱点通常可以使用自动化静态分析工具检测到。许多现代工具使用数据流分析或基于约束的技术来最大限度地减少误报。

## 补充说明与边界

术语
“OS 命令注入”这一短语对不同的人有不同的含义。对一些人来说，它仅指攻击者将命令分隔符注入到被调用程序参数中的情况。对另一些人来说，它指的是任何允许攻击者执行其自行选择的 OS 命令的攻击。这种用法可能包括不受信任的搜索路径弱点 (
CWE-426
)，这些弱点导致应用程序查找并执行攻击者控制的程序。使问题进一步复杂化的是当参数注入 (
CWE-88
) 允许将替代命令行开关或选项插入命令行时的情况，例如 "-exec" 开关，其目的可能是将随后的参数作为命令执行（例如，此 -exec 开关存在于 UNIX "find" 命令中）。然而在后一种情况下，
CWE-88
可能被视为与
CWE-78
链中的主要弱点。
研究差距
需要对 OS 命令注入变体之间的区别进行更多调查，包括其与参数注入 (
CWE-88
) 的关系。在其他与注入相关的问题（如 SQL 注入）中可能存在等效的区别。

## 官方英文定义（核对锚点）

Improper Neutralization of Special Elements used in an OS Command ('OS Command Injection')

The product constructs all or part of an OS command using externally-influenced input from an upstream component, but it does not neutralize or incorrectly neutralizes special elements that could modify the intended OS command when it is sent to a downstream component.
