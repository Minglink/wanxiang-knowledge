# CWE-732：关键资源的权限分配不当

## 缺陷定义

产品对安全关键资源指定的权限方式允许未经授权的主体读取或修改该资源。

## 机制与扩展说明

当资源被赋予的权限设置允许比所需范围更广的参与者访问时，可能会导致敏感信息泄露，或被非预期的第三方修改该资源。当资源涉及程序配置、执行或敏感用户数据时，这一点尤为危险。例如，考虑一个配置错误的云存储账户，它可能被公共或匿名用户读取或写入。

## 可能后果及作用范围

此表指定了与该弱点相关的不同个体后果。“范围”识别被违规的应用安全领域，而“影响”描述如果攻击者成功利用该弱点所产生的负面技术影响。“可能性”提供有关相对于列表中其他后果，特定后果被预期的可能性信息。例如，某种弱点可能极有可能被利用以实现某种影响，但利用它来实现另一种影响的可能性则很低。
影响
详细信息
读取应用程序数据；读取文件或目录
范围：机密性
攻击者可能能够从相关资源中读取敏感信息，例如存储在文件中的凭据或配置信息。
获取特权或冒充身份
范围: 访问控制
攻击者可能能够修改相关资源的关键属性以获得权限，例如将全局可写的可执行文件替换为特洛伊木马。
修改应用程序数据；其他
范围: 完整性，其他
攻击者可能能够破坏或篡改相关资源中的关键数据，例如从数据库中删除记录。

## 预防与缓解措施

阶段
缓解措施
实施
在使用关键资源（如配置文件）时，检查该资源是否具有不安全的权限（例如，任何普通用户都可以修改）[
REF-62
]，如果资源可能已被未经授权的方修改，则生成错误甚至终止软件。
架构与设计
将软件划分为匿名、普通、特权和管理区域。通过仔细定义不同的用户组、权限和/或角色来减少攻击面。将这些与数据、功能和相关资源进行映射。然后相应地设置权限。这将使您能够对资源保持更细粒度的控制。[
REF-207
]
有效性：中等
注意：
这是一种有效的策略。然而，在实践中，当存在许多不同的资源或用户类型，或者应用程序功能变化迅速时，定义这些区域可能会很困难或耗时。
架构与设计；运维
策略：
沙盒或囚笼
在“囚笼 (jail)”或类似的沙盒环境中运行代码，该环境在进程和操作系统之间强制执行严格的边界。这可以有效地限制在特定目录中可以访问哪些文件，或者软件可以执行哪些命令。
操作系统级别的示例包括 Unix chroot 囚笼、AppArmor 和 SELinux。通常，受管代码可能会提供一些保护。例如，Java SecurityManager 中的 java.io.FilePermission 允许软件对文件操作指定限制。
这可能不是一个可行的解决方案，并且它仅将影响限制在操作系统层面；应用程序的其余部分仍可能面临被妥协的风险。
小心避免
CWE-243
以及与囚笼相关的其他弱点。
有效性：有限
注：
此缓解措施的有效性取决于所使用的特定沙盒或囚笼的防护能力，可能仅有助于减小攻击范围，例如限制攻击者使用某些系统调用或限制可访问的文件系统部分。
实现；安装
在程序启动期间，显式地将默认权限或 umask 设置为尽可能严格的设置。还要在程序安装过程中设置适当的权限。这将防止您从任何安装或运行该程序的用户那里继承不安全的权限。
有效性：高
系统配置
对于所有配置文件、可执行文件和库，请确保它们仅能由软件的管理员读取和写入。
有效性：高
文档
不要在文档中建议不安全的配置更改，特别是如果这些配置可以扩展到应用程序范围之外的资源和其他程序时。
安装
不要假设系统管理员会手动将配置更改为软件手册中推荐的设置。
操作；系统配置
策略：
环境强化
确保软件在《美国政府配置基准》(USGCB) [
REF-199
] 或同等加固配置指南下正常运行，许多组织使用这些指南来限制攻击面和已部署软件的潜在风险。
实现；系统配置；操作
在云端存储数据时（例如 S3 存储桶、Azure blob、Google Cloud Storage 等），使用提供商的控制功能来禁用公共访问权限。

## 检测与审计方法

方法
详细信息
自动化静态分析
自动化静态分析在检测系统资源（如文件、目录、共享内存、设备接口等）的权限问题方面可能有效。自动化技术能够检测对修改权限的库函数的使用，然后分析函数调用中包含潜在不安全值的参数。
然而，由于软件的预期安全策略可能允许某些操作具有宽松的权限（例如在 Web 服务器上发布文件），自动化静态分析可能会产生一些误报，即没有任何安全后果或不需要任何代码更改的警告。
当使用自定义权限模型时——例如在公告板系统中定义谁可以在特定论坛中阅读消息——这些很难使用自动化静态分析来检测。可以定义自定义签名来识别实现权限检查和分配的任何自定义函数。
