# CWE-682: 计算错误

## 缺陷定义

该产品执行的计算产生了不正确或意外的结果，而这些结果随后被用于安全关键决策或资源管理中。

## 机制与扩展说明

当产品执行安全关键计算出现错误时，可能会导致错误的资源分配、错误的权限分配或错误的比较等问题。计算错误产生的直接结果往往会引发更严重的问题，例如保护机制失效，甚至导致任意代码执行。

## 预防与缓解措施

阶段
缓解措施
实施
了解您所使用编程语言的底层表示及其与数值计算的交互方式。密切关注字节大小差异、精度、有符号/无符号区别、截断、类型转换、非数值 (NaN) 计算，以及语言如何处理对于其底层表示而言过大或过小的数值。
实施
策略：
输入验证
通过确保数值输入在预期范围内来执行输入验证。强制要求输入满足预期范围的最小值和最大值要求。
实施
对预期操作使用适当的类型。例如，在 C/C++ 中，仅对永远不会为负的值（如高度、宽度或与数量相关的其他数字）使用无符号类型。
架构与设计
策略：
语言选择
使用能够更轻松地处理数字且不会产生意外后果的语言、库或框架。
例子包括安全整数处理包，如 SafeInt (C++) 或 IntegerLib (C 或 C++)。
架构与设计
策略：
库或框架
使用能够更轻松地处理数字且不会产生意外后果的语言、库或框架。
例子包括安全整数处理包，如 SafeInt (C++) 或 IntegerLib (C 或 C++)。
实施
策略：
编译或构建强化
仔细检查编译器警告并消除具有潜在安全影响的问题，例如内存操作中的有符号/无符号不匹配，或使用未初始化的变量。即使该漏洞很少能被利用，单一的失败也可能导致整个系统被攻破。

人工分析
此弱点可以使用需要人工分析的工具和技术进行检测，例如渗透测试、威胁建模以及允许测试人员记录和修改活动会话的交互式工具。

CWE-190
) 或可能对程序产生严重安全影响的类似弱点很有帮助。

注意：
这些可能比纯自动化技术更有效。对于与设计和业务规则相关的弱点，尤其如此。
自动化静态分析
自动静态分析，通常称为静态应用程序安全测试 (SAST)，可以通过分析源代码（或二进制/编译代码）而无需执行它来发现此弱点的某些实例。通常，这是通过构建数据流和控制流的模型，然后搜索连接“源”（输入的起源）和“汇”（数据与外部组件、操作系统等较低层交互的目的地）的潜在易受攻击的模式来完成的。
模糊测试 (Fuzzing)
模糊测试 (Fuzzing) 是一种强大的技术，用于生成大量多样化的输入（随机或按算法生成），并使用这些输入动态调用代码。即使使用随机输入，它也经常能产生意想不到的结果，如崩溃、内存损坏或资源消耗。模糊测试有效地生成了可重复的测试用例，明确指出错误，从而帮助开发人员诊断问题。
有效性：高
