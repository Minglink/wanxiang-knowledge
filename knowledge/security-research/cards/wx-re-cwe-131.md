# CWE-131: 缓冲区大小计算不正确

## 缺陷定义

该产品在分配缓冲区时没有正确计算所需大小，这可能导致缓冲区溢出。

## 可能后果及作用范围

此表指定了与该弱点相关的不同个体后果。“范围”识别被违规的应用安全领域，而“影响”描述如果攻击者成功利用该弱点所产生的负面技术影响。“可能性”提供有关相对于列表中其他后果，特定后果被预期的可能性信息。例如，某种弱点可能极有可能被利用以实现某种影响，但利用它来实现另一种影响的可能性则很低。
影响
详细信息
拒绝服务 (DoS)：崩溃、退出或重启；执行未经授权的代码或命令；读取内存；修改内存
范围：完整性、可用性、机密性
如果在内存分配的上下文中使用不正确的计算，软件可能会创建一个比预期更小或更大的缓冲区。如果分配的缓冲区小于预期，则可能导致越界读取或写入 (
CWE-119
)，从而可能导致程序崩溃、允许执行任意代码或泄露敏感数据。

## 预防与缓解措施

阶段
缓解措施
实施
当为了转换、更改或编码输入而分配缓冲区时，应分配足够的内存以处理可能出现的最长编码。例如，在将“&”字符转换为“&amp;”进行 HTML 实体编码的例程中，输出缓冲区的大小至少需要是输入缓冲区的 5 倍。
实施
了解编程语言的底层表示方式及其与数值计算的交互方式 (
CWE-681
)。密切关注字节大小差异、精度、有符号/无符号区别、截断、类型转换和强制类型转换、“非数值”(NaN) 计算，以及语言如何处理对于其底层表示而言过大或过小的数字。[
REF-7
]
还要注意考虑可能影响数值表示的 32 位、64 位和其他潜在差异。
实施
策略：
输入验证
通过确保数值输入在预期范围内来执行输入验证。强制要求输入满足预期范围的最小值和最大值要求。
架构与设计
对于在客户端执行的任何安全检查，请确保在服务器端重复这些检查，以避免
CWE-602
。攻击者可以通过在检查执行后修改值，或修改客户端以完全移除客户端检查来绕过这些检查。随后，这些被修改的值将被提交到服务器。
实施
当处理包含大小字段后跟原始数据的结构化传入数据时，识别并解决大小字段与数据实际大小之间的任何不一致之处 (
CWE-130
)。
实施
分配使用标记（如字符串中的 NUL 字节）来标记数据结构末尾的内存时，请确保在计算必须分配的总内存量时也包括该标记。
实施
用支持长度参数的类似函数替换无界复制函数，例如用 strncpy 替换 strcpy。如果它们不可用，请创建它们。
有效性：中等
注意：
此方法仍然容易受到计算错误的影响，包括差一错误 (
CWE-193
) 和缓冲区长度计算不正确 (
CWE-131
) 等问题。此外，这仅解决了潜在的溢出问题，资源消耗/耗尽问题仍然可能存在。
实施
在适当的数据类型上使用 sizeof() 以避免
CWE-467
。
实施
针对所需操作使用适当的类型。例如，在 C/C++ 中，仅对永远不可能是负数的值（如高度、宽度或与数量相关的其他数字）使用无符号类型。这将简化验证并减少因意外类型转换而导致的意外情况。
架构与设计
策略：
库或框架
使用经过审查的库或框架，它们不允许此弱点发生，或者提供使此弱点更容易避免的结构 [
REF-1482
]。
使用使处理数字而不产生意外后果变得更容易的库或框架，或者自动跟踪缓冲区大小的缓冲区分配例程。
例如安全整数处理包，如 SafeInt (C++) 或 IntegerLib (C 或 C++)。[
REF-106
]
操作；构建与编译
策略：
环境强化
使用某些编译器或编译器扩展提供的自动缓冲区溢出检测机制。示例包括：Microsoft Visual Studio 的 /GS 标志、Fedora/Red Hat 的 FORTIFY_SOURCE GCC 标志、StackGuard 和 ProPolice，它们提供各种机制，包括基于金丝雀（canary）的检测和范围/索引检查。
D3FEND 中的 D3-SFCV（栈帧金丝雀验证）[
REF-1334
] 详细讨论了基于金丝雀（Canary）的检测。
有效性：纵深防御
注意：
这不一定是一个完整的解决方案，因为这些机制只能检测某些类型的溢出。此外，结果仍然是拒绝服务，因为典型的响应是退出应用程序。
操作；构建与编译
策略：
环境强化
使用在内存中随机排列程序可执行文件和库位置的功能或扩展来运行或编译软件。由于这使得地址不可预测，它可以防止攻击者可靠地跳转到可利用的代码。
例如地址空间布局随机化 (ASLR) [
REF-58
] [
REF-60
] 和位置无关可执行文件 (PIE) [
REF-64
]。如果导入的模块的默认内存地址与其他模块冲突，则可以通过生成随机地址的“重定位”（Windows 称之为“rebasing”，Linux 称之为“prelinking”）过程对导入的模块进行类似的重新对齐 [
REF-1332
]。ASLR 不能与预链接 (prelink) 一起用于库，因为它需要在运行时重定位库，这违背了预链接的目的。
有关这些技术的更多信息，请参阅 D3FEND 中的 D3-SAOR（段地址偏移随机化）[
REF-1335
]。
有效性：纵深防御
注意：
这些技术不能提供完整的解决方案。例如，漏洞利用经常使用泄露内存地址的错误来最大化代码执行的可靠性 [
REF-1337
]。事实证明，侧信道攻击也可以绕过 ASLR [
REF-1333
]。
运营
策略：
环境强化
使用提供数据执行保护（使用硬件 NX 或 XD 位）的 CPU 和操作系统，或在软件中模拟此功能的等效技术，例如 PaX [
REF-60
] [
REF-61
]。这些技术确保执行的任何指令都严格位于属于代码段的内存地址中。
有关这些技术的更多信息，请参阅 D3FEND 中的 D3-PSEP（进程段执行预防）[
REF-1336
]。
有效性：纵深防御
注：
这不是一个完整的解决方案，因为缓冲区溢出可能被用来覆盖附近的变量，以危险的方式修改软件状态。此外，它不能用于需要自修改代码的情况。最后，攻击仍然可能导致拒绝服务，因为典型的响应是退出应用程序。
实施
策略：
编译或构建强化
仔细检查编译器警告并消除具有潜在安全影响的问题，例如内存操作中的有符号/无符号不匹配，或使用未初始化的变量。即使该漏洞很少能被利用，单一的失败也可能导致整个系统被攻破。
架构与设计；运维
策略：
环境强化
使用完成必要任务所需的最低权限运行代码 [
REF-76
]。如果可能，创建仅用于单个任务且权限有限的独立账户。这样，即使攻击成功，攻击者也不会立即获得对软件其余部分或其环境的访问权限。例如，数据库应用程序很少需要以数据库管理员身份运行，特别是在日常操作中。
架构与设计；运维
策略：
沙盒或囚笼
在“囚笼 (jail)”或类似的沙盒环境中运行代码，该环境在进程和操作系统之间强制执行严格的边界。这可以有效地限制在特定目录中可以访问哪些文件，或者软件可以执行哪些命令。
操作系统级别的示例包括 Unix chroot 囚笼、AppArmor 和 SELinux。通常，受管代码可能会提供一些保护。例如，Java SecurityManager 中的 java.io.FilePermission 允许软件对文件操作指定限制。
这可能不是一个可行的解决方案，并且它仅将影响限制在操作系统层面；应用程序的其余部分仍可能面临被妥协的风险。
小心避免
CWE-243
以及与囚笼相关的其他弱点。
有效性：有限
注：
此缓解措施的有效性取决于所使用的特定沙盒或囚笼的防护能力，可能仅有助于减小攻击范围，例如限制攻击者使用某些系统调用或限制可访问的文件系统部分。

## 检测与审计方法

详细信息
自动化静态分析
该弱点通常可以使用自动化静态分析工具检测到。许多现代工具使用数据流分析或基于约束的技术来最大限度地减少误报。
自动静态分析在报告缓冲区计算中的潜在错误时，通常不考虑环境因素。这可能使用户难以确定首先应调查哪些警告。例如，分析工具可能会报告在非 setuid 或其他特殊权限程序中，由命令行参数引发的缓冲区溢出。

## 补充说明与边界

维护
这是一个广泛的类别。一些示例包括
简单的数学错误，
并行计数器更新不正确，
在将一种输入“转换”为另一种格式（例如 URL 规范化或其他可能生成比原始输入更大的结果的转换，即“扩展”）时，未考虑大小差异。
这种详细程度在公开报告中很少见，因此很难找到好的例子。
维护

CWE-682
) 相关，尽管整数溢出 (
CWE-190

## 官方英文定义（核对锚点）

Incorrect Calculation of Buffer Size

The product does not correctly calculate the size to be used when allocating a buffer, which could lead to a buffer overflow.
