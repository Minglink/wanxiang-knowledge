# CWE-79: 网页生成过程中的输入中和不当（“跨站脚本”）

## 缺陷定义

产品在将用户可控的输入放置到供其他用户访问的网页输出中之前，未进行中和处理或中和不当。

## 机制与扩展说明

跨站脚本攻击（XSS）有许多变体，根据不同的术语或涉及不同的攻击拓扑进行特征化。然而，它们都指向同一个根本弱点：在对手和受害者之间对危险输入进行不当的中和处理。

## 可能后果及作用范围

此表指定了与该弱点相关的不同个体后果。“范围”识别被违规的应用安全领域，而“影响”描述如果攻击者成功利用该弱点所产生的负面技术影响。“可能性”提供有关相对于列表中其他后果，特定后果被预期的可能性信息。例如，某种弱点可能极有可能被利用以实现某种影响，但利用它来实现另一种影响的可能性则很低。

跨站脚本攻击最常见的攻击方式涉及泄露用户 cookie 中存储的私密信息，例如会话信息。通常，恶意用户会制作一个客户端脚本，当被 Web 浏览器解析时，它会代表受害者执行某些活动，指向攻击者控制的系统（例如将所有网站 cookie 发送到指定的电子邮件地址）。如果受害者拥有管理该网站的管理员权限，这对网站来说尤其危险。该脚本会被访问网站的每个用户加载并运行。由于请求运行脚本的网站有权访问相关的 cookie，恶意脚本也同样拥有权限。

输入验证
假设所有输入都是恶意的。采用“接受已知良好”的输入验证策略，即使用严格符合规范的可接受输入列表。拒绝任何不严格符合规范的输入，或将其转换为符合规范的内容。
在执行输入验证时，考虑所有潜在相关的属性，包括长度、输入类型、可接受值的全部范围、缺失或额外的输入、语法、跨相关字段的一致性以及对业务规则的符合性。作为业务规则逻辑的一个例子，“boat”在语法上可能是有效的，因为它只包含字母数字字符，但如果输入只预期包含“red”或“blue”等颜色，则它无效。
不要仅仅依赖查找恶意或畸形输入。这很可能会遗漏至少一种不受欢迎的输入，尤其是当代码环境发生变化时。这可能给攻击者留出绕过预期验证的空间。不过，黑名单对于检测潜在攻击或确定哪些输入由于严重畸形而应被直接拒绝是有用的。
在动态构建网页时，使用严格的允许列表（allowlist），根据请求中参数的预期值限制字符集。所有输入都应经过验证和清理，不仅是用户应该指定的参数，还包括请求中的所有数据，包括隐藏字段、cookie、头部、URL 本身等。导致 XSS 漏洞持续存在的常见错误是仅验证预计会被网站重新显示的字段。经常会看到来自请求的数据被应用程序服务器或开发团队未预料到的应用程序反射。此外，当前未被反射的字段可能会被未来的开发人员使用。因此，建议验证所有 HTTP 请求部分。
请注意，适当的输出编码、转义和引用是防止 XSS 的最有效解决方案，尽管输入验证可能提供一些纵深防御。这是因为它有效地限制了输出中会出现的内容。输入验证并不总是能防止 XSS，特别是如果您需要支持可能包含任意字符的自由格式文本字段。例如，在聊天应用程序中，心形表情符号（“<3”）可能会通过验证步骤，因为它很常用。但是，它不能直接插入网页，因为它包含“<”字符，需要对其进行转义或以其他方式处理。在这种情况下，剥离“<”可能会降低 XSS 的风险，但它会导致不正确的行为，因为表情符号不会被记录。这看起来可能是一个小的不便，但在希望表示不等式的数学论坛中，这将更重要。
即使您在验证中犯了错误（例如忘记了 100 个输入字段中的一个），适当的编码仍然很可能会保护您免受基于注入的攻击。只要不孤立地进行，输入验证仍然是一种有用的技术，因为它可以显著减少您的攻击面，让您能够检测到一些攻击，并提供适当编码无法解决的其他安全好处。
确保您在应用程序内的定义明确的接口执行输入验证。即使组件被重用或移动到其他地方，这也将有助于保护应用程序。

## 背景机制

同源策略（Same Origin Policy）规定，浏览器应将给定网站或“源”上运行的脚本可访问的资源限制为与客户端上该网站关联的资源，而不是任何其他网站或“源”的客户端资源。其目标是防止一个网站修改或读取无关网站的内容。由于万维网涉及许多网站之间的交互，因此浏览器强制执行此策略非常重要。
当提到 XSS 时，网站的域大致相当于连接客户端上与该网站关联的资源。也就是说，域可以被认为浏览器为用户与此特定网站的交互所存储的所有资源。

## 补充说明与边界

关系
XSS 和 CSRF (
CWE-352
) 之间可能存在密切关系。攻击者可能使用 CSRF 来诱骗受害者向服务器提交包含 XSS 有效载荷的请求。MySpace 上的 Samy 蠕虫就是一个众所周知的例子 [
REF-956
]。该蠕虫利用 XSS 将恶意 HTML 序列插入用户的个人资料中，并添加攻击者为 MySpace 好友。该受害者的 MySpace 好友随后会执行该有效载荷以修改他们自己的个人资料，导致蠕虫呈指数级传播。由于受害者并没有故意插入恶意脚本，因此 CSRF 是根本原因。
适用平台
XSS 缺陷在 Web 应用程序中非常常见，因为需要开发人员具备高度的纪律性才能避免它们。
其他
XSS 的攻击方法可能会根据 XSS 的类型和攻击者的目标而有所不同。
反射型 XSS 利用（类型 1）
发生在攻击者诱导受害者将危险内容提供给易受攻击的 Web 应用程序，该内容随后被反射回受害者并由 Web 浏览器执行。提供恶意内容最常见的机制是将其作为 URL 中的参数包含在内，该 URL 被公开发布或直接通过电子邮件发送给受害者。以此方式构建的 URL 构成了许多网络钓鱼计划的核心，攻击者以此说服受害者访问指向易受攻击网站的 URL。在网站将攻击者的内容反射回受害者后，该内容便由受害者的浏览器执行。
在
存储型 XSS 利用（类型 2）
中，注入恶意内容的最佳位置是显示给许多用户或特别感兴趣的用户的区域。感兴趣的用户通常在应用程序中具有提升的权限，或与攻击者有价值的敏感数据交互。如果这些用户中的一个执行了恶意内容，攻击者可能能够代表用户执行特权操作或获得对属于用户的敏感数据的访问权限。例如，攻击者可能会将 XSS 注入日志消息中，当管理员查看日志时，该消息可能无法得到妥善处理。
基于 DOM 的 XSS（类型 0）
通常涉及发送到客户端的、受服务器控制的受信任脚本，例如在用户提交表单之前对表单进行完整性检查的 JavaScript。如果服务器提供的脚本处理用户提供的数据，然后将其注入回网页（例如使用动态 HTML），那么基于 DOM 的 XSS 就是可能的。
其他
攻击者经常使用各种方法对攻击的恶意部分进行编码，例如 URL 编码或 Unicode，以便请求看起来不那么可疑。网络钓鱼攻击可用于模拟可信网站并诱骗受害者输入密码，从而允许攻击者入侵受害者在该网站上的账户。
其他
跨站脚本 (XSS) 漏洞发生在：
不可信数据进入 Web 应用程序，通常来自 Web 请求。
Web 应用程序动态生成包含此不可信数据的网页。
在页面生成过程中，应用程序不会阻止数据包含可由 Web 浏览器执行的内容，例如 JavaScript、HTML 标签、HTML 属性、鼠标事件、Flash、ActiveX 等。
受害者通过 Web 浏览器访问生成的网页，该页面包含使用不可信数据注入的恶意脚本。
由于脚本来自 Web 服务器发送的网页，受害者的 Web 浏览器会在 Web 服务器域的上下文中执行恶意脚本。
这有效地违反了 Web 浏览器同源策略的初衷，该策略规定一个域中的脚本不应能够访问不同域中的资源或运行代码。

## 官方英文定义（核对锚点）

Improper Neutralization of Input During Web Page Generation ('Cross-site Scripting')

The product does not neutralize or incorrectly neutralizes user-controllable input before it is placed in output that is used as a web page that is served to other users.
