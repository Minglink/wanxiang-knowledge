# CWE-89: SQL 命令中使用的特殊元素中和不当（“SQL 注入”）

## 缺陷定义

产品使用来自上游组件且受外部影响的输入构建 SQL 命令的全部或部分内容，但在将该命令发送到下游组件时，未能中和或错误地中和了可能修改预期 SQL 命令的特殊元素。如果无法充分删除或引用用户可控输入中的 SQL 语法，生成的 SQL 查询可能会导致这些输入被解释为 SQL 代码，而不是普通的业务数据。

## 可能后果及作用范围

此表指定了与该弱点相关的不同个体后果。“范围”识别被违规的应用安全领域，而“影响”描述如果攻击者成功利用该弱点所产生的负面技术影响。“可能性”提供有关相对于列表中其他后果，特定后果被预期的可能性信息。例如，某种弱点可能极有可能被利用以实现某种影响，但利用它来实现另一种影响的可能性则很低。
影响
详细信息
执行未经授权的代码或命令
范围：机密性、完整性、可用性
攻击者可以执行系统命令，通常是通过更改 SQL 语句，将输出重定向到可以随后执行的文件中。
读取应用程序数据
范围：机密性
由于 SQL 数据库通常存储敏感数据，机密性丢失是 SQL 注入漏洞的常见问题。
获取权限或假冒身份；绕过保护机制
范围：身份验证
如果使用不当的 SQL 命令来检查用户名和密码或执行其他类型的身份验证，则有可能在不知道密码的情况下以其他用户身份连接到产品。
绕过保护机制
范围: 访问控制
如果授权信息存储在 SQL 数据库中，则有可能通过成功利用 SQL 注入漏洞来更改这些信息。
修改应用程序数据
范围：完整性
正如可以读取敏感信息一样，通过 SQL 注入攻击，也可以修改甚至删除这些信息。

例如，考虑使用 Hibernate 或 Enterprise Java Beans 等持久层，如果使用得当，可以提供针对 SQL 注入的显著保护。

策略：
参数化
如果可用，请使用自动强制执行数据和代码分离的结构化机制。这些机制可能能够自动提供相关的引用、编码和验证，而不是依赖开发人员在每次生成输出时提供此功能。
使用预编译语句、参数化查询或存储过程处理 SQL 查询。这些功能应接受参数或变量，并支持强类型。不要在这些功能中使用“exec”或类似功能动态构建和执行查询字符串，因为这可能会重新引入 SQL 注入的可能性。[
REF-867
]
架构与设计；运维
策略：
环境强化
使用完成必要任务所需的最低权限运行代码 [
REF-76
]。如果可能，创建仅用于单一任务且权限受限的隔离帐户。这样，即使攻击成功，攻击者也无法立即访问软件的其他部分或其环境。例如，数据库应用程序很少需要以数据库管理员身份运行，尤其是在日常操作中。
具体来说，在创建 SQL 数据库的用户帐户时遵循最小权限原则。数据库用户应仅拥有使用其帐户所需的最低权限。如果系统需求表明用户可以读取和修改自己的数据，则限制其权限，使他们无法读取/写入他人的数据。对所有数据库对象使用尽可能严格的权限，例如存储过程仅限执行。
架构与设计
对于在客户端执行的任何安全检查，请确保在服务器端重复这些检查，以避免
CWE-602
。攻击者可以通过在检查执行后修改值，或修改客户端以完全移除客户端检查来绕过这些检查。随后，这些被修改的值将被提交到服务器。
实施
策略：
输出编码
虽然使用动态生成的查询字符串、代码或将控制与数据混合的命令存在风险，但有时可能无法避免。请正确引用参数并转义这些参数中的任何特殊字符。最保守的方法是转义或过滤所有未通过极其严格的白名单检查的字符（例如，除字母数字或空格以外的所有字符）。如果仍需使用某些特殊字符（如空格），请在转义/过滤步骤后将每个参数用引号括起来。注意参数注入（
CWE-88
）。
与其构建新的实现，不如在数据库或编程语言中使用现有功能。例如，Oracle DBMS_ASSERT 包可以检查或强制参数具有某些属性，从而使其不易受到 SQL 注入攻击。对于 MySQL，C 和 PHP 中均提供了 mysql_real_escape_string() API 函数。
实施
策略：
输入验证
假设所有输入都是恶意的。采用“接受已知良好”的输入验证策略，即使用严格符合规范的可接受输入列表。拒绝任何不严格符合规范的输入，或将其转换为符合规范的内容。
在执行输入验证时，考虑所有潜在相关的属性，包括长度、输入类型、可接受值的全部范围、缺失或额外的输入、语法、跨相关字段的一致性以及对业务规则的符合性。作为业务规则逻辑的一个例子，“boat”在语法上可能是有效的，因为它只包含字母数字字符，但如果输入只预期包含“red”或“blue”等颜色，则它无效。
不要仅仅依赖查找恶意或畸形输入。这很可能会遗漏至少一种不受欢迎的输入，尤其是当代码环境发生变化时。这可能给攻击者留出绕过预期验证的空间。不过，黑名单对于检测潜在攻击或确定哪些输入由于严重畸形而应被直接拒绝是有用的。
在构建 SQL 查询字符串时，使用严格的允许列表（Allowlist），根据请求中参数的预期值限制字符集。这将间接限制攻击范围，但该技术不如正确的输出编码和转义重要。
请注意，适当的输出编码、转义和引用是防止 SQL 注入的最有效解决方案，尽管输入验证可能提供一些纵深防御。这是因为它有效地限制了输出中会出现的内容。输入验证并不总是能防止 SQL 注入，特别是如果您需要支持可能包含任意字符的自由格式文本字段。例如，“O'Reilly”这个名字可能会通过验证步骤，因为它在英语中是一个常见的姓氏。但是，它不能直接插入数据库，因为它包含“'”撇号字符，需要对其进行转义或以其他方式处理。在这种情况下，剥离撇号可能会降低 SQL 注入的风险，但它会导致不正确的行为，因为记录的名字会出错。
在可行时，最安全的方法可能是完全不允许元字符，而不是转义它们。这将提供一些纵深防御。数据进入数据库后，后续进程可能会忽略在使用前转义元字符，并且您可能无法控制这些进程。

策略：
通过转换执行
当可接受对象（如文件名或 URL）的集合有限或已知时，创建从一组固定输入值（如数字 ID）到实际文件名或 URL 的映射，并拒绝所有其他输入。
实施
确保错误消息仅包含对目标受众有用的最小细节，而不包含其他信息。消息需要在过于隐晦（可能使用户感到困惑）和过于详细（可能泄露不该泄露的信息）之间取得平衡。消息不应泄露用于确定错误的具体方法。攻击者可以利用详细信息来完善或优化其原始攻击，从而增加成功的可能性。
如果必须详细记录错误，请将其记录在日志消息中，但要考虑如果攻击者能够查看日志消息会发生什么。密码等高度敏感的信息绝不应保存到日志文件中。
避免使用不一致的消息，以免意外向攻击者透露内部状态，例如用户账户是否存在。
在 SQL 注入的上下文中，揭示 SQL 查询结构的错误消息可以帮助攻击者定制成功的攻击字符串。
运营
策略：
防火墙
使用可以检测针对此弱点攻击的应用程序防火墙。在代码无法修复（因为由第三方控制）的情况下，作为应用更全面的软件保障措施时的紧急预防措施，或者为了提供纵深防御，这可能是有益的 [REF-1481]。
有效性：中等
注意：
应用程序防火墙可能无法覆盖所有可能的输入向量。此外，攻击者可能会使用绕过保护机制的攻击技术，例如使用仍可被接收输入的组件处理的畸形输入。根据功能的不同，应用程序防火墙可能会无意中拒绝或修改合法请求。最后，定制可能需要一些人工投入。
操作；实现
策略：

## 官方英文定义（核对锚点）

Improper Neutralization of Special Elements used in an SQL Command ('SQL Injection')

The product constructs all or part of an SQL command using externally-influenced input from an upstream component, but it does not neutralize or incorrectly neutralizes special elements that could modify the intended SQL command when it is sent to a downstream component. Without sufficient removal or quoting of SQL syntax in user-controllable inputs, the generated SQL query can cause those inputs to be interpreted as SQL instead of ordinary user data.
