# CWE-427：不受控制的搜索路径元素

## 缺陷定义

产品使用固定或受控的搜索路径来查找资源，但该路径中的一个或多个位置可能处于非预期参与者的控制之下。

## 机制与扩展说明

虽然此弱点可能出现在任何类型的资源中，但它通常是在产品使用目录搜索路径查找可执行文件或代码库时引入的，而该路径包含可由攻击者修改的目录，例如“/tmp”或当前工作目录。
在基于 Windows 的系统中，当使用不包含完全限定路径的 DLL 名称调用 LoadLibrary 或 LoadLibraryEx 函数时，该函数会遵循包含两个可能不受控制的路径元素的搜索顺序：
程序加载所在的目录
当前工作目录
在某些情况下，攻击可以远程进行，例如使用 SMB 或 WebDAV 网络共享时。
该路径中的一个或多个位置可能包括 Windows 驱动器根目录或其子目录。这通常存在于假设根目录 (/) 或其子目录 (/etc 等) 为受控状态的 Linux 代码中，或者存在于递归访问父目录的代码中。在 Windows 中，驱动器根目录及其部分子目录默认具有较弱的权限，这使它们处于不受控制的状态。
在某些基于 Unix 的系统中，创建的 PATH 变量可能包含一个空元素，例如通过将空变量拼接到 PATH 中。此空元素可被解释为等同于当前工作目录，这可能是一个不可信的搜索元素。
在软件包管理框架（例如 npm、RubyGems 或 PyPi）中，框架可能会识别对第三方库或其他包的依赖，然后咨询包含所需包的存储库。框架可能会在私有存储库之前搜索公共存储库。攻击者可以通过在公共存储库中放置一个与私有存储库中包同名的恶意包来利用这一点。搜索路径可能并不直接由依赖该框架的开发人员控制，但这种搜索顺序实际上包含了一个不可信的元素。

使用需要显式路径的其他函数。利用任何其他现成的、需要显式路径的函数是避免此问题的安全方法。例如，C 语言中的 system() 不需要完整路径，因为 shell 可以利用 PATH 环境变量来查找程序，而 execl() 和 execv() 则需要完整路径。

## 补充说明与边界

关系
与不可信搜索路径 (
CWE-426
) 不同（后者本质上涉及对控制范围定义的控制，即搜索路径的修改），此条目关注的是一个固定的控制范围，其中该范围的某一部分可能处于攻击者控制之下（即攻击者无法修改搜索路径，但该路径的一个元素可能处于攻击者控制之下）。
理论性

CWE-668
或
CWE-610
，这表明控制范围模型可能需要增强或澄清。
