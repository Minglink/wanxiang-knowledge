# CWE-95: 动态评估代码中指令中和不当（“Eval 注入”）

## 缺陷定义

产品从上游组件接收输入，但在动态求值调用（例如 "eval"）中使用该输入之前，未中和或错误地中和了代码语法。

## 可能后果及作用范围

此表指定了与该弱点相关的不同个体后果。“范围”识别被违规的应用安全领域，而“影响”描述如果攻击者成功利用该弱点所产生的负面技术影响。“可能性”提供有关相对于列表中其他后果，特定后果被预期的可能性信息。例如，某种弱点可能极有可能被利用以实现某种影响，但利用它来实现另一种影响的可能性则很低。
影响
详细信息
读取文件或目录；读取应用程序数据
范围：机密性
注入的代码可能会访问受限的数据或文件。
绕过保护机制
范围: 访问控制
在某些情况下，可注入的代码会控制身份验证；这可能导致远程漏洞。
获取特权或冒充身份
范围: 访问控制
注入的代码可以访问攻击者原本被直接阻止访问的资源。
执行未经授权的代码或命令
范围：完整性、机密性、可用性、其他
代码注入攻击几乎在所有情况下都会导致数据完整性丧失，因为注入的控制平面数据总是伴随着数据的调用或写入。此外，代码注入通常会导致执行任意代码，或者至少修改可执行的代码。
隐藏活动
范围：不可抵赖性
注入的控制代码所执行的操作通常不会被记录。

## 预防与缓解措施

阶段
缓解措施
架构与设计；实现
策略：
重构
如果可能，重构代码以完全不需要使用 eval()。
实施
策略：
输入验证
假设所有输入都是恶意的。采用“接受已知良好”的输入验证策略，即使用严格符合规范的可接受输入列表。拒绝任何不严格符合规范的输入，或将其转换为符合规范的内容。
在执行输入验证时，考虑所有潜在相关的属性，包括长度、输入类型、可接受值的全部范围、缺失或额外的输入、语法、跨相关字段的一致性以及对业务规则的符合性。作为业务规则逻辑的一个例子，“boat”在语法上可能是有效的，因为它只包含字母数字字符，但如果输入只预期包含“red”或“blue”等颜色，则它无效。
不要仅仅依赖查找恶意或畸形输入。这很可能会遗漏至少一种不受欢迎的输入，尤其是当代码环境发生变化时。这可能给攻击者留出绕过预期验证的空间。不过，黑名单对于检测潜在攻击或确定哪些输入由于严重畸形而应被直接拒绝是有用的。
实施
输入在被验证之前应解码并规范化为应用程序当前的内部表示形式 (
CWE-180
,
CWE-181
)。确保您的应用程序不会无意中对相同的输入进行两次解码 (
CWE-174
)。此类错误可能会通过在检查后引入危险输入来绕过允许列表方案。使用诸如 OWASP ESAPI 规范化控制之类的库。
考虑执行重复的规范化，直到您的输入不再发生变化。这将避免双重解码和类似场景，但它可能会无意中修改允许包含正确编码的危险内容的输入。
实施
对于 Python 程序，通常建议使用 ast.literal_eval() 函数而不是 eval，因为它被专门设计用于避免执行代码。然而，攻击者仍可能通过深度嵌套的结构导致过度的内存或堆栈消耗 [
REF-1372
]，因此 Python 文档不建议对不受信任的数据使用 ast.literal_eval() [
REF-1373
]。
有效性：不推荐的常见做法

## 官方英文定义（核对锚点）

Improper Neutralization of Directives in Dynamically Evaluated Code ('Eval Injection')

The product receives input from an upstream component, but it does not neutralize or incorrectly neutralizes code syntax before using the input in a dynamic evaluation call (e.g. "eval").
