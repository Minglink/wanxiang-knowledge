# CWE-20: 不当的输入验证

## 缺陷定义

产品接收输入或数据，但未验证或错误地验证了输入是否具有安全且正确处理数据所需的属性。

## 机制与扩展说明

输入验证是一种常用的技术，用于检查潜在的危险输入，以确保输入在代码内处理或与其他组件通信时是安全的。
输入可包含：
原始数据 - 字符串、数字、参数、文件内容等。
元数据 - 关于原始数据的信息，例如标头或大小。
数据可以是简单的，也可以是结构化的。结构化数据可以由许多嵌套层组成，由元数据和原始数据的组合构成，并包含其他简单或结构化数据。
许多原始数据或元数据的属性在输入代码时可能需要进行验证，例如：
指定的数量，如大小、长度、频率、价格、速率、操作次数、时间等。
隐含或派生的数量，例如文件的实际大小而非指定的大小。
索引、偏移量或更复杂数据结构中的位置。
散列表、关联数组等的符号键或其他元素。
格式正确性，即语法正确性 - 符合预期的语法。
词法标记正确性 - 符合被视为标记的规则。
指定或派生的类型 - 输入的实际类型（或输入看起来的样子）。
一致性 - 各个数据元素之间、原始数据和元数据之间、引用之间的一致性等。
符合特定领域的规则，例如业务逻辑。
等价性 - 确保等价的输入被同等对待。
真实性、所有权或其他关于输入的证明，例如用于证明数据来源的加密签名。
数据的隐含或派生属性通常必须由代码本身计算或推断。推导这些属性时的错误可被视为导致输入验证不当的一个因素。

## 补充说明与边界

关系
CWE-116
和
CWE-20
有着密切的联系，因为根据结构化消息的性质，适当的输入验证可以间接防止特殊字符改变结构化消息的含义。例如，通过验证数字 ID 字段应该只包含 0-9 字符，程序员可以有效地防止注入攻击。
存在多种将潜在危险输入转换为安全内容的技术，这不同于“验证”，后者是一种检查输入是否已经安全的技术。CWE 用户在进行根本原因分析时需要谨慎，以确保问题确实是一个输入验证问题。
术语
“输入验证”一词非常通用，但它的使用方式多种多样。在某些情况下，它的使用会掩盖真正的底层弱点或以其他方式隐藏链式和复合关系。
有些人将“输入验证”用作通用术语，涵盖了确保输入适当的许多不同中和技术，例如过滤，即试图删除危险输入（与
CWE-790
相关）；编码/转义，即试图确保当输入包含在对另一个组件的输出中时不会被误解（与
CWE-116
相关）；或规范化，它通常间接删除原本危险的输入。其他人则在更窄的上下文中仅将其用作“检查输入是否符合预期而不改变它”。CWE 使用这种狭义的解释。
请注意，“输入验证”对不同的人或在不同的分类方案中有着截然不同的含义。在引用此 CWE 条目或映射到它时必须小心。例如，某些弱点可能涉及在攻击者本不应该提供输入时无意中给予了攻击者对输入的控制权，但这有时被称为输入验证。
最后，必须强调的是，输入验证和输出转义之间的区别往往是模糊的。开发人员必须小心了解其中的区别，包括输入验证为何并不总是足以防止漏洞，特别是在必须支持自由格式文本等不太严格的数据类型时。考虑一个 SQL 注入场景，其中一个人的姓氏被插入到查询中。姓氏“O'Reilly”很可能会通过验证步骤，因为它在英语中是一个常见的姓氏。然而，这个有效的名字不能直接插入到数据库中，因为它包含“'”撇号字符，需要对其进行转义或以其他方式转换。在这种情况下，删除撇号可能会降低 SQL 注入的风险，但它会产生不正确的行为，因为记录的名字是错误的。

截至 2020 年，此条目的使用频率高于预期，并且是频繁混淆的来源。它正在为 CWE 4.1 及后续版本进行积极修改。
维护
诸如验证、数据转换和中和等概念正在不断完善，因此
CWE-20
与其他条目（如
CWE-707
）之间的关系在未来版本中可能会发生变化，同时也会更新漏洞理论文档。
维护
输入验证——无论是缺失还是不正确——是安全开发中一个如此基本且广泛的部分，以至于它隐含在许多不同的弱点中。传统上，许多安全专业人员将缓冲区溢出和 XSS 等问题归类为输入验证问题。然而，输入验证不一定是避免此类问题的唯一可用保护机制，在某些情况下它甚至是不够的。CWE 团队已开始在“研究概念”(View-1000) 视图中以链式方式捕捉这些细微差别 (
CWE-1000

Improper Input Validation

The product receives input or data, but it does
        not validate or incorrectly validates that the input has the
        properties that are required to process the data safely and
        correctly.
