# CWE-129: 不正确的数组索引验证

## 缺陷定义

产品在计算或使用数组索引时使用了不可信的输入，但产品未对索引进行验证或验证不正确，无法确保索引引用的是数组内的有效位置。

## 可能后果及作用范围

此表指定了与该弱点相关的不同个体后果。“范围”识别被违规的应用安全领域，而“影响”描述如果攻击者成功利用该弱点所产生的负面技术影响。“可能性”提供有关相对于列表中其他后果，特定后果被预期的可能性信息。例如，某种弱点可能极有可能被利用以实现某种影响，但利用它来实现另一种影响的可能性则很低。
影响
详细信息
DoS：崩溃、退出或重启
范围：完整性、可用性
使用超出数组边界的索引极有可能导致相关内存甚至指令的损坏，如果数值位于有效内存区域之外，则会导致崩溃。
修改内存
范围：完整性
如果损坏的内存是数据而非指令，系统将继续使用不正确的数值运行。
修改内存；读取内存
范围：机密性、完整性
使用超出数组边界的索引也可能触发越界读取或写入操作，或对错误对象进行操作；即“缓冲区溢出”并不总是唯一结果。这可能导致敏感数据的泄露或修改。
执行未经授权的代码或命令
范围：完整性、机密性、可用性
如果攻击者可以有效控制可访问的内存，则可能像标准缓冲区溢出一样执行任意代码，并且如果可以精确控制索引，甚至无需使用大量输入。
DoS：崩溃、退出或重启；执行未经授权的代码或命令；读取内存；修改内存
范围：完整性、可用性、机密性
单一故障可能导致数组索引溢出 (
CWE-788
) 或下溢 (
CWE-786
)。后续后果取决于越界执行的操作类型，但可能导致敏感信息泄露、系统崩溃或可能导致任意代码执行。

## 预防与缓解措施

阶段
缓解措施
架构与设计
策略：
输入验证
使用输入验证框架，如 Struts 或 OWASP ESAPI 验证 API。请注意，使用框架并不能自动解决所有输入验证问题；请留意因误用框架本身而可能产生的弱点 (
CWE-1173
)。
架构与设计
对于在客户端执行的任何安全检查，请确保在服务器端重复这些检查，以避免
CWE-602
。攻击者可以通过在检查执行后修改值，或修改客户端以完全移除客户端检查来绕过这些检查。随后，这些被修改的值将被提交到服务器。
尽管客户端检查在服务器端安全方面提供的益处微乎其微，但它们仍然很有用。首先，它们可以支持入侵检测。如果服务器收到的输入本应被客户端拒绝，这可能表明存在攻击。其次，客户端错误检查可以向用户提供有关有效输入期望值的有用反馈。第三，可能会减少偶然输入错误导致的服务器端处理时间，尽管这通常节省很少。
需求
策略：
语言选择
使用一种不允许此弱点发生或提供使此弱点更容易避免的结构的语言。
例如，Ada 允许程序员约束变量的值，而 Java 和 Ruby 等语言则允许程序员在访问越界索引时处理异常。
操作；构建与编译
策略：
环境强化
使用在内存中随机排列程序可执行文件和库位置的功能或扩展来运行或编译软件。由于这使得地址不可预测，它可以防止攻击者可靠地跳转到可利用的代码。
示例包括地址空间布局随机化 (ASLR) [
REF-58
] [
REF-60
] 和位置无关可执行文件 (PIE) [
REF-64
]。如果导入模块的默认内存地址与其他模块冲突，可以使用随机生成的地址进行重排，这一过程在 Windows 中称为“重基 (rebasing)”，在 Linux 中称为“预链接 (prelinking)” [
REF-1332
]。库的 ASLR 不能与预链接结合使用，因为它需要在运行时重定位库，这违背了预链接的初衷。
有关这些技术的更多信息，请参阅 D3FEND 中的 D3-SAOR（段地址偏移随机化） [
REF-1335
]。
有效性：纵深防御
注：
这些技术并不能提供完整的解决方案。例如，漏洞利用经常使用泄露内存地址的错误，以最大化代码执行的可靠性 [
REF-1337
]。此外，已有研究表明旁路攻击可以绕过 ASLR [
REF-1333
]。
运营
策略：
环境强化
使用提供数据执行保护（使用硬件 NX 或 XD 位）的 CPU 和操作系统，或在软件中模拟此功能的等效技术，如 PaX [
REF-60
] [
REF-61
]。这些技术确保任何执行的指令都仅位于代码段内的内存地址。
有关这些技术的更多信息，请参阅 D3FEND 中的 D3-PSEP（进程段执行预防） [
REF-1336
]。
有效性：纵深防御
注：
这不是一个完整的解决方案，因为缓冲区溢出可能被用来覆盖附近的变量，以危险的方式修改软件状态。此外，它不能用于需要自修改代码的情况。最后，攻击仍然可能导致拒绝服务，因为典型的响应是退出应用程序。
实施
策略：
输入验证
假设所有输入都是恶意的。采用“接受已知良好”的输入验证策略，即使用严格符合规范的可接受输入列表。拒绝任何不严格符合规范的输入，或将其转换为符合规范的内容。
在执行输入验证时，考虑所有潜在相关的属性，包括长度、输入类型、可接受值的全部范围、缺失或额外的输入、语法、跨相关字段的一致性以及对业务规则的符合性。作为业务规则逻辑的一个例子，“boat”在语法上可能是有效的，因为它只包含字母数字字符，但如果输入只预期包含“red”或“blue”等颜色，则它无效。
不要仅仅依赖查找恶意或畸形输入。这很可能会遗漏至少一种不受欢迎的输入，尤其是当代码环境发生变化时。这可能给攻击者留出绕过预期验证的空间。不过，黑名单对于检测潜在攻击或确定哪些输入由于严重畸形而应被直接拒绝是有用的。
访问用户控制的数组索引时，请使用目标数组范围内的严格值范围。确保不允许使用负值。即，同时验证可接受值的最小值和最大值。
实施
在调用跨语言边界的代码时（例如从解释型语言到原生代码），请务必格外小心地验证所有输入。这可能会在语言边界之间产生意外的交互。确保没有违反所接口语言的任何期望。例如，即使 Java 本身不容易受到缓冲区溢出的影响，但在调用原生代码时提供大的参数也可能触发溢出。
架构与设计；运维
策略：
环境强化
以完成必要任务所需的最低权限运行代码 [
REF-76
]。如果可能，创建仅用于单一任务的权限受限的隔离账户。这样，成功的攻击不会立即让攻击者访问软件的其他部分或其环境。例如，数据库应用程序很少需要在日常操作中以数据库管理员身份运行。
架构与设计；运维
策略：
沙盒或囚笼
在“囚笼 (jail)”或类似的沙盒环境中运行代码，该环境在进程和操作系统之间强制执行严格的边界。这可以有效地限制在特定目录中可以访问哪些文件，或者软件可以执行哪些命令。
操作系统级别的示例包括 Unix chroot 囚笼、AppArmor 和 SELinux。通常，受管代码可能会提供一些保护。例如，Java SecurityManager 中的 java.io.FilePermission 允许软件对文件操作指定限制。
这可能不是一个可行的解决方案，并且它仅将影响限制在操作系统层面；应用程序的其余部分仍可能面临被妥协的风险。
小心避免
CWE-243
以及与囚笼相关的其他弱点。
有效性：有限
注：
此缓解措施的有效性取决于所使用的特定沙盒或囚笼的防护能力，可能仅有助于减小攻击范围，例如限制攻击者使用某些系统调用或限制可访问的文件系统部分。

## 检测与审计方法

方法
详细信息
自动化静态分析
该弱点通常可以使用自动化静态分析工具检测到。许多现代工具使用数据流分析或基于约束的技术来最大限度地减少误报。
在报告越界内存操作时，自动化静态分析通常不考虑环境因素。这可能导致用户难以确定哪些警告应优先调查。例如，分析工具可能会报告源自命令行参数的数组索引错误，而这些参数在不应以 setuid 或其他特殊权限运行的程序中出现。
有效性：高
注：
这不是一个完美的解决方案，因为 100% 的准确性和覆盖率是不可行的。
自动化动态分析
可以使用与软件交互的动态工具和技术来检测此弱点，这些工具使用带有许多多样化输入的大型测试套件，例如模糊测试 (fuzzing)、健壮性测试和故障注入。软件运行可能会变慢，但不应变得不稳定、崩溃或产生错误的结果。
自动化动态分析
使用在编译期间集成以插入与内存安全错误相关的运行时错误检查机制的工具，例如用于 C/C++ 的 AddressSanitizer (ASan) [
REF-1518
]。
有效性：中等
注：
需要精心设计的输入才能到达包含错误的各种代码路径，例如由模糊测试工具生成的输入。此外，这些工具可能会降低性能，并且它们仅报告错误情况——而不是导致错误的原始失误。
黑盒测试
黑盒方法可能无法在有限的时间限制内获得所需的代码覆盖率，并且即使动态测试成功，也可能不会产生任何明显的副作用。

## 补充说明与边界

关系
在会自动扩展数组（当使用大于数组大小的索引时）的语言（如 JavaScript）中，此弱点可能先于不受控制的内存分配 (
CWE-789

理论性

## 官方英文定义（核对锚点）

Improper Validation of Array Index

The product uses untrusted input when calculating or using an array index, but the product does not validate or incorrectly validates the index to ensure the index references a valid position within the array.
